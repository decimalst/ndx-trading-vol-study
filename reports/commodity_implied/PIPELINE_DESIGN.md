# Commodity monthly pipeline: prospective generated-data contract

This component is written before any commodity numerical source, cohort, fit, or outcome access. It is a producer scheduling component, not an independent mathematical verifier. No comparison is registered by this document. All existing frozen source and earlier reports remain unchanged.

`build_panel(features, targets, config=None)` accepts already-built features on the complete observed QQQ calendar. Features require the fixed 22 model columns (including the intercept) and `commodity_cutoff_date`; extra provenance columns are ignored. Targets have exactly `y` and `target_end` on the identical native datetime index. The five-session endpoint is checked against full-calendar position, including rows with missing targets. Commodity cutoff metadata must equal the immediately previous full-calendar session, with dates before 2009-01-02 represented as unknown. Complete model rows require all 22 finite named values and known cutoff metadata. The pipeline does not reconstruct feature formulas or alter the calendar.

The default origin interval is 2016-01-01 through 2025-10-20. Development origins end on 2019-12-31 and their targets must end by that date. Evaluation origins begin on 2020-01-01 and their targets must end by source end, 2025-10-20. The default common training floor is 1000. Exact configuration keys are `origin_start`, `origin_end`, `development`, `evaluation`, `source_end`, and `minimum_train`. Smaller generated-fixture date intervals and positive training floors are permitted; configuration source bounds cannot exceed 2025-10-20 or precede the commodity source floor. Native naive midnight dates, unique ordered calendar entries, positive observed targets, nonboolean real numeric inputs, and an exactly-one observed intercept are required. Missing numerical inputs are retained; infinity, invalid dates, and malformed endpoints abort.

Every requested calendar month receives a schedule row, including months with no observed origin or no complete feature row. The earliest complete feature row fixes the monthly query independently of its target. Training consists of every earlier complete row whose positive finite label ends by the immediately previous observed calendar session. The same complete 22-column training and application rows serve market, matched, and candidate arms. Every complete requested origin is an application, including origins outside a phase or without a scoreable target. All offsets use the original full-calendar position modulo five; missingness never compresses the calendar. The model component supplies three separate fixed OLS fits and arm-specific smearing; this pipeline does not change that estimator.

Any scheduled fit below the declared floor raises ValueError-compatible `InsufficientDataError` with `INSUFFICIENT_DATA` in its message. The exception exposes full requested `coverage` and all planned `schedules`, with no partial forecasts. All coverage `scored` flags are false, complete rows have `attempt_aborted`, and incomplete rows retain `incomplete_features`. The failed month has `insufficient_training`; subsequent complete months remain `not_attempted`. Previous completed schedule rows may show `fitted`, but no successful attempt payload is returned. Numerical or model failure likewise aborts the attempt; no supported-month skipping, fallback, or clipping is allowed.

Success returns exactly `applications`, `panel`, `coverage`, `schedules`, and `fits`. Applications and coverage are in origin order. Panel rows use origin order then market, matched, candidate. Schedules and fits are chronological. Applications retain origin, fit origin, previous-session training cutoff, training count, commodity cutoff, full-calendar offset, phase, and all three forecasts. Fits retain month, ISO fit/cutoff dates, exact ISO training and application origin lists, training count, and the model audits. No claims release identities, release support count, or weekly weighting are inherited.

Coverage contains every requested observed origin, exact missing-feature names in fixed model order, commodity cutoff, target endpoint/observation/phase eligibility, fit links, and one status. Successful-attempt status precedence is `incomplete_features`, `outside_phase`, `target_not_mature` (unknown endpoint), `missing_target`, `target_after_phase_cutoff`, then `scored`. Incomplete rows have no fit link. All complete unscored rows retain predictions and fit links. Scored rows contain ordinary QLIKE `y/p - log(y/p) - 1`; every scored and unscored prediction must be finite and positive. Arithmetic failure aborts without a floor. Date outputs are datetime64[ns], counts and offsets nullable Int64, flags boolean, numerical outputs float64.

The component deliberately reuses only the frozen claims pipeline's generic ISO/date and numeric validation, prediction-array validation, and QLIKE arithmetic helpers. Commodity schedules, common row selection, clock validation, coverage, and support exception handling are new. The new commodity model module supplies the already-declared three OLS arms. These are disclosed producer dependencies, not independent verification.

The 16 prewritten synthetic tests target query-label blindness, strict previous-session maturity, common-row selection, unchanged calendar offsets, development versus evaluation censoring, missing/outside-phase applications, empty months, full-attempt support failure with retained coverage, exact metadata clocks, invalid model forecasts and arithmetic, native datetime units, and integration with all three actual model arms. Fixtures contain only invented values. `PIPELINE_RED.log` records the actual missing-module failure before implementation. All 16 tests passed on the first implementation in 0.332 seconds (`PIPELINE_FIRST_IMPLEMENTATION.log`); subsequent edits only applied formatting and lint corrections. `PIPELINE_GREEN.log` records the final focused tests and lint checks. This component does not validate source vintages, calculate inference, freeze artifacts, or authorize empirical scoring.
