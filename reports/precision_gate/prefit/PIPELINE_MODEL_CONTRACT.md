# Fixed precision-gate scheduler and expert contract

This new producer uses generated tests first; `PIPELINE_MODEL_RED.log` records both missing modules before implementation. No historical feature, target, sample-support or forecast array was accessed. The source ceiling remains October 20, 2025. The existing market builder supplies the twelve ordered columns `const,lrv_d,lrv_w,lrv_m,lev_d,lev_w,lev_m,liv,lvix,term,xasset_stress,market_stress`; extra columns are ignored. State is exactly `lrv_d-lrv_m`, recorded when a forecast is issued.

`fit_experts(train_features, train_y, apply_features, *, train_positions, cutoff_position, adaptive_half_life=252)` returns `predictions` and `fits`, each keyed `base,adaptive`. Positions are unique increasing nonnegative original-calendar positions, no later than the cutoff. Both experts use the exact same caller-selected rows. Base weights are one. Adaptive weights are `exp2(-(cutoff_position-train_position)/adaptive_half_life)`, without normalizing the saved weight vector. Zero/nonfinite weights are fatal. Each expert separately computes weighted population feature means/scales, standardizes eleven non-intercept columns, and solves square-root-weighted log-target least squares with relative rank cutoff 1e-12. All scales must exceed 1e-12 and rank must be twelve. Exact matching-weight Duan smearing is `logsumexp(log(weights)+residual)-log(sum(weights))`. No feature, expert or numerical fallback is available.

Each expert audit has exactly `feature_names`, named `coefficients`, named `feature_means` and `feature_scales` excluding the intercept, `singular_values`, `rank`, `rank_relative_cutoff`, raw `weights`, `weight_sum`, `log_smearing`, `normal_equation_max_abs`, `n_train`, `n_application`. Coefficients apply to the standardized design; singular values describe its square-root-weighted matrix. The normal-equation audit is `max(abs(Z.T @ (weights*residual)/sum(weights)))`.

`build_panel(features, targets, config=None)` validates one unchanged, unique, ascending native date index, real finite-or-NaN common features and positive finite-or-NaN targets. Targets have exactly `y,target_end`; every endpoint must equal the fifth next full-calendar position, including NaT at the last five positions. A finite target cannot lack an endpoint. Complete date metadata is validated before numerical arithmetic. The exact ten configuration keys are `issuance_start,origin_start,origin_end,source_end,development,evaluation,minimum_train,adaptive_half_life,gate_window,gate_minimum_train`. Production defaults are issuance January 4, 2010; scoring January 1, 2016 through October 20, 2025; development 2016–2019; evaluation 2020 through the ceiling; and 1000/252/1260/252 for the four integer settings. Smaller generated-only settings are supported by this pure component; the root protocol binds production settings.

Every requested month has a schedule. Its first common12-complete origin and full set of complete application positions are chosen from features before reading query targets. The training cutoff is the preceding full observed session. Training comprises every earlier complete origin with a positive observed target whose endpoint is no later than the cutoff. An insufficient expert month before `origin_start` is `expert_warmup`, with no predictions. Insufficiency at or after `origin_start` raises `InsufficientDataError`; no partial experiment qualifies. Scale/rank/arithmetic failures are fatal even during earlier issuance. Earliest eligible training history can precede issuance start.

At each fitted month, both gates select exactly the previously issued base/adaptive/state records with original positions `fit_position-gate_window <= position < fit_position`, positive observed labels and endpoints mature by the cutoff. They never synthesize forecasts retrospectively, refill a missing date, compress the window to retained rows, or substitute a later fitted state. Below the fixed pair floor, both coefficients are `[0,0]`, shared gate status `cold_start`, and both gated predictions equal base. Otherwise both frozen-core fits use the same records, once with `constant=True` and once with `constant=False`, and shared status `fitted`. All complete application origins receive all four forecasts, including missing or not-yet-mature labels and origins outside scoring phases. Cold starts remain in scored comparisons. Scored origins and their target endpoints must both lie in the same declared phase. Offsets are original full-calendar positions modulo five.

## Output schema

The exact five keys are `applications,panel,coverage,schedules,fits`. DataFrame date columns use Timestamp/NaT with datetime64[ns]; count columns use pandas nullable Int64; boolean flags are bool. Frames retain chronological order. Panel rows are ordered by origin then arm insertion order `base,adaptive,constant,contextual`.

- Applications: `origin,fit_origin,training_cutoff,train_n,gate_n,gate_status,state,offset,phase,pred_base,pred_adaptive,pred_constant,pred_contextual`.
- Panel: `origin,model,prediction,y,loss,target_end,fit_origin,training_cutoff,train_n,gate_n,gate_status,state,offset,phase`. Loss is unmodified QLIKE `y/prediction-log(y/prediction)-1`, checked finite and positive in its arguments.
- Coverage: `origin,phase,feature_complete,missing_features,state,offset,target_end,target_observed,target_within_phase,issued,scored,status,fit_origin,training_cutoff,gate_status`. It retains every reference origin in the issuance window. Missing names are pipe-joined in fixed MARKET order. `phase` is development/evaluation/outside_phase; `target_observed` means finite y; `target_within_phase` means a known endpoint within that origin's phase. Unissued fit/cutoff dates are NaT and gate status is `not_issued`. Status precedence is incomplete_features, attempt_aborted, expert_warmup, outside_phase, target_not_mature, missing_target, target_after_phase_cutoff, scored.
- Schedules: `month,status,fit_origin,training_cutoff,requested_n,feature_complete_n,application_n,train_n,gate_n,gate_status`. Status is not_attempted/no_complete_origin/no_requested_origins/expert_warmup/insufficient_training/fitted. `application_n` counts actually issued origins and is zero in warmup; `feature_complete_n` counts planned origins. No-fit counts train_n/gate_n are null and dates NaT. Warmup retains train_n but gate_n null and gate_status not_issued.
- Fits: one JSON-native dictionary per attempted month with at least one complete origin, including warmups. Exact keys are `month,status,fit_origin,training_cutoff,train_origins,train_positions,train_n,planned_application_origins,application_origins,gate_train_origins,gate_train_positions,gate_n,gate_status,expert_audits,gate_audits`. Date lists are ISO strings, positions refer to the full calendar. Warmups retain training/planned identities, no actual application/gate identities, gate_n zero, gate_status not_issued, and both audit mappings null. Fitted expert_audits have base/adaptive. Fitted gate_audits have constant/contextual, each the frozen core dictionary plus status=fitted; cold-start dictionaries have exactly status/coefficients/constant/n_train, with n_train equal to the retained mature pair count.

On expert support failure, `InsufficientDataError.produced` retains the five-key diagnostic payload, partial issued applications, all planned schedules and attempted fit audits, with an empty scored panel. `coverage` and `schedules` are also direct exception attributes. This preserves already issued records without presenting a successful partial result.

The prewritten expert tests compare both fits against direct raw weighted normal equations and independently computed smearing, test exact log-linear recovery and application independence, and reject rank, scale, position and weight-underflow failures. Pipeline tests exercise actual frozen gate calls, literal mature/issued membership, full-calendar windows and offsets, target-blind scheduling, future-label poisoning, expert warmup, retained cold starts, common phase endpoints, unscored issuance, missing months and honest failures. No empirical support or model test is represented by these generated checks.

## Prefreeze failure-retention addition

Root review identified that an optimizer or arithmetic exception could lose earlier issued months held in memory. A new generated test injects failure on the third non-cold gate fit, after earlier monthly issuance, and requires preservation of those exact earlier applications, the failed month/stage, completed expert audits and an empty scored panel. `PIPELINE_FAILURE_RETENTION_RED.log` preserves the missing-error-API failure before implementation.

`PipelineExecutionError` now exposes `produced`, `month`, `stage`, `coverage` and `schedules`; `InsufficientDataError` subclasses it and preserves its prior interface. The root runner can catch the base error and save the five-key partial payload. Numerical failures during a monthly fit mark that month's schedule and fit `execution_failed`, retain completed expert/gate audit portions and eligible memberships, and never issue fallback predictions. Stages identify expert_fit, gate_membership, constant/contextual_gate_fit, constant/contextual_gate_prediction, prediction_validation or application_issuance. A later scored-panel arithmetic failure retains the completed issuance payload with stage scored_panel and an empty panel. Completed-output schemas, mathematical rules and production settings are unchanged.
