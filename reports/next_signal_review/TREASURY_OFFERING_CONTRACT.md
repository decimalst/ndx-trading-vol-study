# Stated offering amount: three-document reconciliation contract

This component reconciles one explicitly labelled original offering amount across the announcement PDF, announcement XML and result XML. It does not infer an offering from awards, outstanding principal, bid-to-cover, SOMA, or other totals; it does not admit a source history or establish an event relationship by matching amounts. Existing identity and financial parsers remain unchanged.

## Source mapping fixed before tests/application

The preserved pilot announcement text was inspected only for literal fields/layout and source strings. It labels the amount `Offering Amount` followed by a full-dollar string, separately from `Currently Outstanding`, and includes unrelated offering-language footnotes plus SOMA/FIMA inclusion fields. The exact XML leaf is the direct, unnamespaced `AuctionAnnouncement/OfferingAmount`, including within the result XML; it is not an `AuctionResults` accepted-total field. Both ordinary new-issue and reopening announcement layouts were inspected before the synthetic tests. No real amount parser was applied and no historical amount arithmetic was performed.

The parent obtained the referenced schema at `data/source_discovery/treasury_auction/offering_schema_v1/body.xsd`, SHA256 `7e093d19820bf0beeb1b22fa347cda0059593a664597b14c5ce992c14c189d72`. It declares `OfferingAmount` as `GreaterThanZeroFloatType` without a unit annotation. **That schema does not authenticate a universal billions unit.** The fixed conversion contract is an explicit mapping hypothesis: one XML unit represents 1,000,000,000 USD. Each successful reconciliation must agree exactly with the independently parsed, explicitly dollar-labelled PDF value. The multiplier is never selected or changed by row, magnitude, fit or a search over scales. A mismatch fails; it cannot trigger unit inference.

## API and identity boundary

- `parse_announcement_offering(text, *, identity)` returns `offering_amount_usd` as an integer, `source_unit: "USD"`, and the original `source_token`.
- `parse_xml_offering(raw, *, role, identity, unit)` accepts role `announcement` or `result` and requires the literal unit contract `USD_BILLIONS`. It returns the integer USD amount, that declared source unit and the original XML source token.
- `reconcile_offering(pdf_text, announcement_xml, result_xml, *, identities, xml_unit)` requires three exact identity entries keyed `announcement_pdf`, `announcement_xml`, `result_xml`; checks every identity before financial conversion; then requires exact agreement among all three USD values. It returns `status: VERIFIED_STATED_OFFERING_AGREEMENT`, `offering_amount_usd`, `unit: USD`, per-source parse evidence, the explicit scale limitation and `source_admitted: false`.

PDF identity has exact keys `auction_date`, `announcement_date`, `cusip`. XML identity adds `announced_cusip`: `None` declares an absent/empty `AnnouncedCUSIP`, while a nonempty string declares its exact expected value separately from `CUSIP`. Calendar dates and uppercase nine-character identities are explicit inputs, not inferred from numerical agreement. PDF release/embargo header must match its own announcement date; its labelled auction date and CUSIP must match its own expected identity. XML dates and both CUSIP roles must match that document's own expected identity. Exact container and field roles remain enforced.

The caller must independently authenticate that these expected document identities belong to the same offering. An initial announced CUSIP, final substituted CUSIP, or original/rescheduled auction date can differ when explicitly expected for the corresponding document. This component neither invents that relationship nor weakens the frozen `check_event_identity`. The frozen strict function can continue rejecting a substituted source when passed one common CUSIP. Amount reconciliation under separately expected identities does not supersede source-clock, announcement/result lineage, original-vintage or regular-auction checks.

The existing bounded XML identity reader and PDF header metadata reader are reused for safe source decoding and dated-header evidence. Financial parsing and cross-format offering arithmetic are implemented independently of the existing result-amount parsers.

## Exact value and layout rules

XML input is bounded UTF-8 bytes using the existing exact root/identity decoder, which rejects malformed XML, DTD/entity declarations and aliased/nested identity fields. Announcement role has no result container; result role has exactly one. There must be exactly one `OfferingAmount` anywhere in the document, as an unnamespaced direct leaf of its sole `AuctionAnnouncement`, with no nested content or attributes. Namespace aliases, duplicates and copies hidden under another section fail. Its token is unsigned plain decimal text with no surrounding whitespace, exponent, separator, nonfinite spelling or sign.

The fixed billion-to-dollar conversion uses decimal digits and integer arithmetic, without float conversion or Decimal-context multiplication. Extra fractional digits are permitted only when they cannot produce a fractional dollar. The result must be a strictly positive integral USD amount; actual zero, negative values, missing values and fractional dollars fail. Per-source unit declarations remain visible even though all returned comparison amounts are USD integers.

PDF input is bounded extracted text, with one exact offering-announcement title, unique CUSIP/date identity fields, and one exact labelled `Offering Amount` row. Its dollar token requires conventional comma grouping and unsigned integer dollars; malformed grouping, aliases, duplicate rows, nonfinite spellings, decimals or trailing material fail. Other field labels containing the words “Offering Amount,” currently outstanding amounts, the reopening marker and ordinary numbered offering footnotes are not alternative amount fields. No missing amount can be filled from them.

## Prospective verification

The original eleven generated test methods were written before the source module. The genuine missing-module RED run is retained in `TREASURY_OFFERING_RED.log`; the final focused test/style outcome is retained in `TREASURY_OFFERING_GREEN.log`. Invented fixtures cover new issues/reopening footnotes, the three distinct source roles, original/final and rescheduled identity expectations, all-identity checks before conversion, missing/duplicate/nested/namespaced/wrong-section fields, malformed dollars, fixed-unit and fractional-dollar rejection, precision beyond binary floats under a small Decimal context, disagreement in any one source, and absence of an accepted-total fallback.

After the first implementation passed those eleven checks, local review found that a second empty PDF field label could be ignored beside a valid row. A twelfth method was prewritten and reproduced two failures, for empty duplicate offering and auction-date labels; that RED output was appended without altering the initial failure evidence. The new row helper was then corrected to count empty labels and reject them. This correction did not alter any frozen source or broaden a numerical contract. No real numerical application is authorized by the synthetic checks alone; the parent performs the paired-source pass only after its next checkpoint.
