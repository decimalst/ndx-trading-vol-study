# Treasury original-release and correction-clock review

Reviewed 2026-09-08. **The official archive provides a credible document-ledger route for qualified exploratory use. No actual unresolved corrected or replaced auction result was identified in this review.** This metadata-only review does not itself complete admission because result bodies and known special notices were deliberately not inspected. The next evidence test is agreement of dated primary release content with auction identity and a complete review of known correction notices; missing cryptographic version IDs are not a source-blocking condition.

This follows the [independent gap review](/Users/byrons/code/trading-vol/ndx-vol-experiment/reports/next_signal_review/INDEPENDENT_GAP_REVIEW.md), which remains unchanged. Scope here was official documentation, archive-page HTML, and the page's linked JavaScript for date/link construction. No auction-result PDF/XML body, numerical auction-data endpoint, market array, cohort, feature, fit, or score was requested. Only this new document was written.

## What the official sources establish

TreasuryDirect describes its archive as current and historical auction announcement/result press releases, with non-TIPS releases from July 27, 1998. That is a concrete official historical-document service. The visible text does not describe an immutable version repository, state that earlier result versions are retained after correction, or supply a complete correction history. [Archive overview](https://www.treasurydirect.gov/auctions/announcements-data-results/announcement-results-press-releases/), [previous announcements/results](https://www.treasurydirect.gov/auctions/announcements-data-results/announcement-results-press-releases/previous-announcements-and-results/).

The auction timeline identifies an operational release event: from January 2003, official release time was considered the time the result XML was delivered to the Federal Reserve Information Technology server. It also distinguishes the initially later bidder-category addendum from the main result, and says that category statistics were released simultaneously with the main result from September 2004. This supports the existence of a real publication clock. It does not make that historical delivery log available through the current archive page. [Treasury auction timeline, 2003–2004 entries](https://www.treasurydirect.gov/research-center/timeline/auctions/).

TreasuryDirect's information-quality page provides a formal process for requesting corrections and reconsideration of its website/publications. It says correspondence may be posted and reserves discretion not to post some material. The associated published request/response page is a correspondence collection, not a stated comprehensive log of every auction-data correction. Its displayed examples concern other information and cannot establish that auction results were never corrected. [Data-quality process](https://www.treasurydirect.gov/data_quality.htm), [published requests and responses](https://www.treasurydirect.gov/legal-information/data-quality/guidance/).

The official regulations overview also says that the amendment effective August 8, 2022 removed references to press releases, among other changes. That synopsis is not evidence that historical PDFs disappeared or were rewritten; it is a reason not to infer an unchanging document-format guarantee from earlier descriptions of publication. [Treasury auction-regulations overview](https://www.treasurydirect.gov/laws-and-regulations/auction-regulations-uoc/).

## Concrete archive metadata findings

The archive table is populated dynamically. Its linked official script requests the current Treasury securities search with a year range and `dateFieldName=auctionDate`. The inspected source defines these fields: CUSIP, security term/type, announcement date, auction date, announcement PDF filename, competitive-results PDF filename, noncompetitive-results PDF filename, special-announcement filename(s), and announcement/result XML filenames. A single competitive-results filename is represented; the special-announcement field can contain multiple comma-separated names. The script provides no original-version ID, superseded-version chain, or per-version original publication timestamp. These are observations about the exposed interface, not proof that Treasury possesses no such records internally. [Official archive table script, lines 10–30 and 33–77](https://www.treasurydirect.gov/scripts/auctions-section/annceresult.js).

The PDF path builders use the announcement year for announcements and auction year for competitive/noncompetitive results. Special-announcement links are supported, but a special announcement is not automatically a result correction. Its role would need classification from its actual document. The `R`-type result filename slot must not be interpreted as a “revised” flag. No specific annual auction row or result body was decoded here; only the route and field semantics were inspected. [Same archive script](https://www.treasurydirect.gov/scripts/auctions-section/annceresult.js).

A second official script, used for the current announcement display, labels an announcement as “Uploaded” using `announcementDate` when a special announcement is present, but `updatedTimestamp` in the other branch. Separate special notices use `updateTimestamp`. This directly demonstrates that a displayed upload date is not a uniform first-publication timestamp. It concerns that renderer; it does not establish the exact update semantics of every historical result record. [Official announcement renderer, lines 43–59](https://www.treasurydirect.gov/scripts/auctions-section/press_secannpr.js).

Targeted official-domain searches for revised/corrected auction-result documentation did not identify an auction-specific promise of retaining superseded versions or a comprehensive original/correction register. This bounded failure to find a policy must not be restated as evidence that corrections do not occur. No corrected-auction example is authenticated by this review.

## Can a document ledger support the feature?

**Yes, conditionally; the ledger must track versions and knowledge dates, not just auction dates.** The required evidence and treatment are:

| Case | Historical feature treatment |
| --- | --- |
| Dated primary result/category content agrees with the archive's auction identity, and the known-notice review finds no unresolved contradictory version | This can support an original-release ledger row for qualified exploratory use. Preserve its bytes and independently parsed identity/value fields. Eligibility begins at the first QQQ session strictly after the later required document's supported release date. A contemporaneously published cryptographic hash is not required. |
| Original and correction are both retained, and the correction has a distinct supported release date | Keep both versions and their relationship. Do not apply the correction before its own publication. The previously proposed first-report feature retains the originally published value; later corrections are audit records, not permission to rewrite its past 12-auction reference history. |
| Only a corrected current result is available, with no recoverable original | The first-report feature is unknown. Do not backdate the corrected value to the auction day or pretend an extra one-session delay repairs the missing original. |
| Only an index/filename date has been inspected, or the primary document's identity/date contradicts it | Read and reconcile the primary release before admission; keep a demonstrated unresolved identity/date conflict unknown. A current hash, PDF creation field, retrieval time, or HTTP Last-Modified is not a substitute for primary release content. |
| A special notice concerns a schedule or terms rather than allocation correction | Record the appropriate role; do not merge it into a numeric revision chain solely because the archive lists it beside a result. |

A future ledger should separately retain auction/CUSIP identity, original security term and reopening lineage, document role, official index link, body release date/time, evidence supporting public availability, capture time, byte hash, correction relationship, and whether a superseded original was recovered when needed. Dated originating-agency content, consistent identity, and a documented review of the complete known-notice set are useful historical evidence even without a cryptographic timestamp or separate contemporaneous mirror. Hashes establish reproducibility of today's capture. If a second current-format export agrees, that adds cross-format validation, not independent historical timing evidence. The generic possibility of an undisclosed silent edit remains an archival limitation; absent positive evidence, it is not a reason to mark every row unresolved or demand unattainable certainty.

The one-session lag remains appropriate for a close-based exploratory design once the original document's publication date is supported. It accommodates ordinary intraday result/addendum timing without asserting an executable auction-time quote. It does not resolve a later revision or a missing publication history. The proposed post-2009 source floor addresses one documented bidder-classification transition; it cannot substitute for this separate version audit.

## Recommendation and stopping condition

**Advance the bounded documentary pilot; do not label this route clock-blocked on the current evidence.** A concrete prospective test is to select an ordinary eligible result in each of 2010, 2016, and 2025 through October 20, plus an indexed reopening/special-notice case, using only dates and document-role metadata. Prewrite synthetic parser tests, then check that primary headers identify the auction/CUSIP, result role, public-release date and the required accepted bidder categories. Reconcile the original offering and any separate category addendum. These are format/identity checks, not a search over interesting allocation values.

The all-types annual index inventory should retain every special-notice link, including notices outside the selected tenor subset that could refer back to an eligible auction. Classify the complete known relevant notice set for delays, schedule changes, corrections, and replacements before accepting the full ledger. If the inventory or primary content identifies a correction, preserve both versions when available and apply the explicit first-report rule. A bounded metadata search finding no correction is weaker than completing that indexed-notice review, but neither finding is proof of universal immutability.

If the pilot succeeds, the same declared rules can govern a controlled full source pass and independent ledger reconciliation. Only concrete missing required documents, unresolved date/identity disagreements, or a demonstrated correction whose original cannot be recovered should make the affected first-report inputs unknown. Failure of subsequent prospectively fixed coverage/support requirements can then stop the experiment. Do not infer present source-ineligibility solely from the lack of a version API. The eventual evidence class must disclose the current-capture archival limitation, while distinguishing it from any actual unresolved corrections. No contact, credentials, purchase, auction-data acquisition, or model run was initiated here.
